# dsh-plugin-task-board

DeepSeek Harness 的**规划视图**插件：往侧边栏加一行「规划视图」，里面是三个页面。

| 页面 | 回答什么问题 |
|---|---|
| **看板** | 哪个窗口在等我？四列（进行中 / 待审阅 / 待办 / 归档），一张卡一个主任务 |
| **甘特** | 最近 21 天谁跑了、跑了多久？一根条形是一个任务，条形里的深色段是每一次真实执行 |
| **进度** | 我这一摊子整体什么状态、有没有东西卡住？ |

这个插件存在的理由只有一个：**多窗口并行的时候，人容易忘记哪个窗口在等自己。**
所以三页全是「一眼扫过去」的形态，没有需要展开三层才看得到的数字。

**会话也算任务。** 没有挂卡的那些会话（随手问一句、临时排查一个报错）照样进三个视图，
带一枚「会话」角标 —— 大多数窗口其实属于这一类，不显示出来就等于没看。
详见下面「没有任务卡的会话，也当成任务」。

**卡片边框上的颜色是这一页的重点**：它回答「它为什么停在这儿」。
红＝这一轮没走完（外力，或者你自己按的停止）、橙＝它在等你做一个动作、
绿＝它宣布目标达成、蓝＝跑完一轮等你发话、**橙红呼吸＝它下面还压着东西**（子代理在等）。
**待审阅里每一张卡都有颜色**：跑完了（会话跑完一轮、或者任务卡上次执行成功）是蓝的 ——
**跑完了就是跑完了，不是「闲着」**；只剩确实没有消息的（没跑完过一整轮、或者读不出来）
才是那个中性的闲着色，不落回默认的灰边框 —— 一列里就剩几张有颜色，看上去像数据没读出来。
颜色**只在「待审阅」列出现**，唯一的例外是橙红那一种 —— 它的全部意义就是「你看不见它」。
**每一种纯色的卡都有一道光沿着边框跑**（红 / 橙 / 绿 / 蓝 / 闲着）。

**它对任务卡的要求是零。** 账本里没有「目标 / 场景 / 背景 / 验收」这几个字段，
所以这四条是**推出来的**：先按规则从真实字段算，算不出来可以交给模型归纳，你还能自己改。
每一句都标着它是哪一级来的。装上看板里那张卡什么样，这里就什么样，不需要你补任何东西。

## 装上

这是一个标准的 DSH 插件包。装法和别的第三方插件一样：让包名进 profile 的
`dsh.profile.bundles`，然后 `pnpm install`。

```bash
# 1. 把包放进 profile 的依赖里（路径或 git 地址都行）
cd ~/.dsh/profiles/<你的 profile>
pnpm add file:/绝对路径/dsh-plugin-task-board
#    或者：pnpm add git+ssh://git@github.com/hujiuyuan/dsh-plugin-task-board.git

# 2. 把包名加进 profile 的 package.json —— 这一步不能省
#    "dsh": { "profile": { "bundles": [ ..., "dsh-plugin-task-board" ] } }
```

**第 2 步漏了的后果是：插件装上了、依赖都在、但界面上什么都不出现。**
`cordis.patch.yml` 只有在包名进了 `bundles` 之后才会被读到。

改完重启 DSH。

## 数据从哪来

插件有两条数据来源，**优先用第一条，拿不到才退到第二条**：

1. **任务看板的客户端服务**（cordis 服务名 `taskBoard`）。这是正路：读的是任务看板自己
   维护的内存镜像，那边一改，这边立刻跟着变。顶栏右边显示「看板实时」。
2. **账本快照**（`$DSH_HOME/task-board/ledger-v2.json`）。任务看板是另一个插件，它可能
   没装、没启用、或者启动时降级了。这时本插件的宿主半体读一份账本快照给界面。
   顶栏右边显示「账本快照 · 只读」，并且**不会自动更新**，要手动点「刷新」。

   账本格式（`schemaVersion`）**认的是一个区间不是某一个值**：看板自己会把老账本逐代
   迁移上来，而我们退回读的是盘上那份原文，所以第 2 到第 6 代都读。认不出的那一代
   不猜字段，横幅上写明「文件里是第 N 代、本插件认得哪几代」，并给出两条出路。

另外还读**宿主的会话目录**（`ctx.sessions.list`），用来把没有卡的会话补成任务行。
它跟上面两条是**并列的**：账本一条都读不到时，会话照常出现在界面上。

**账本只读。** 本插件从不直接改 `ledger-v2.json`——那是任务看板的私有文件。要往
看板里写（新建卡、改内容、挪列）走的是看板自己给的口子，见下面「写操作」那一节。

## 「目标 / 场景 / 背景 / 验收」是怎么来的

账本里**没有**这四个字段。但空着比没有更糟——用户会以为页面坏了。

所以这四条是**补出来的**，而且每一句都标着它是从哪一级来的：

| 标记 | 意思 | 离线可用 |
|---|---|---|
| **按账本推的** | 从真实字段按写死的规则算出来的。每一句都能追到账本里的一条记录 | ✅ 永远在 |
| **模型归纳** | 模型读了这张卡的素材之后写的。可能不准 | 需要一个可用的模型 |
| **你改的** | 人手工写的。**压过上面两级**，模型重跑也盖不掉 | ✅ |
| **账本原文** | 账本里真有的字段，原样显示 | ✅ |

具体每个字段：

| 字段 | 按账本推 | 模型归纳 |
|---|---|---|
| 目标 | 执行提示的第一句 → 说明的第一句 → 标题 | 要达成什么，一句话 |
| 使用场景 | 定时规则 + 历次执行是定时还是手工发起 | 什么时候会用它 |
| 背景 | 创建时间 + 结算时间 + 跑了几次成几次 | 来龙去脉 |
| 验收 | 从执行记录反推的**已经发生的事实**（成功几次、失败的原话） | 可核验的条目 |
| 优先级 | 规则算的：有失败=紧急，在跑=高，有启用的定时=中，其余=低。**不问模型** | — |

优先级不问模型是故意的：模型看不到「跑没跑、失败没失败」这些唯一该依据的东西，
问它只会得到一个听着合理、跟事实无关的答案。

### 模型那条路怎么走

```
浏览器                    宿主进程                 模型
  │  素材（标题/说明/提示/    │                       │
  ├─ 执行结果/错误原文）─────►│                       │
  │                          ├── llm.stream ────────►│
  │                          │◄── 一段文本 ──────────┤
  │◄─ 四条（剥围栏、取第一个  │                       │
  │   JSON、字段逐个查类型）  │                       │
```

三条硬规矩：

1. **浏览器半体不直接跟模型说话**（这是宿主定的规矩）。它把素材 POST 给插件的宿主半体。
2. **模型的回复是不可信文本。** 剥代码围栏 → 取第一个平衡的 `{}` → 逐个字段查类型。
   解析不出来不是错误：回一个空的，前端退回规则推导那一层。
3. **一次调用只问一次，结果按指纹缓存。** 卡的素材没变就不重复问——
   每打开一次抽屉就问一遍模型，用户很快就不会再点那个按钮了。

**降级的四种情况，每一种都只影响模型那一层：** 宿主没提供 `llm` 服务 / 任务没绑模型
也问不出模型目录 / 模型报错 / 模型超时。这四种下「用模型补全」按钮禁用或报错，
**下面四条照常按账本推出来**，页面不会空。

### 存在哪

归纳结果和人工改动存在 **`$DSH_HOME/dsh-plugin-task-board/enrichment.json`**，
和任务看板自己的 `task-board/` 目录并列，**绝不往里塞东西**。

为什么不写回账本的 `integrations` 字段（卡片上本来就有一格是专门留给扩展的）：
那一格要经看板的写入契约才能碰，而这份归纳结果是**本插件的**缓存和人工输入，
跟看板里那张卡的内容没关系。写进去等于把我们的中间产物塞进别人的数据结构里。

### 「周期目标」也是算出来的

原型里有一张「周期目标」卡（本周目标 3/5）。真实数据里**没有目标**这种字段，
但**有排期**——而排期本身就隐含了一个期望：「每天 9 点跑一次」就等于这一周该跑 7 次。

所以进度视图里那个「应跑 N 次」是从已启用的 cron 推出来的，**不是编的**。

一条硬规则：**一天跑不止一次的排期不算目标。** 一个每 15 分钟跑一次的看门任务，
一周的「应跑」是 672 次，写出来就是纯噪音，还会让人以为排期坏了。一天至多一次的
才成立。认不出来的 cron 写法一律不算，并在界面上写明「另有 N 条没算进目标」。

### 关于「定时 / 手动」

执行记录里只写了「是哪个会话发起的」。**定时触发的那一刻没有发起会话，所以没有发起者。**
本插件据此推断「没有发起者 = 定时」，界面上标成「定时」的地方都带着这个前提说明——
它是推断不是记录。

## 写操作

四个动作：**新建卡 / 改标题说明提示 / 挪列 / 改排期**。

前三个写**不经过账本文件**，走任务看板自己公开的扩展契约：

```
浏览器 ──POST /api/dsh-plugin-task-board/task──► 宿主半体
                                                  │ ctx.get('taskBoard')
                                                  │   .registerExtension({ id, apiVersion: 1, start })
                                                  ▼
                                          host.tasks.create / patchContent / setStatus
                                                  │
                                          （看板自己的校验、自己的落盘）
```

**为什么非要绕这一圈。** 直接改 `ledger-v2.json` 会绕过看板的两道闸：创建时的字段校验，
和「已经跑过的卡不许再改内容」这条规矩。绕过去写出来的是一份看板自己都读不懂的账本，
而且要到它下次启动时才炸。

三条边界：

1. **看板不在场就没有写。** 它的宿主半体没加载、或者扩展开关关着时，写入口**一律灰着
   并写明原因**，不做「点了才拒绝」——一个能按但按下去只说「不行」的按钮比灰着更气人。
   界面靠 GET 同一条路由探就绪状态。
2. **一次只做一件事。** 没有批量写、没有事务。每次调用都是看板那边一次完整的校验加落盘，
   我们不在中间插自己的逻辑。
3. **认不出的动作直接拒绝**，不当没看见——那样前端会以为成功了。看板拒绝时它抛的错
   **原话带回**（「这张卡已经开始跑过了……」），不转述：它比我们清楚为什么不行。

### 排期走的是**另一条路**，这事要说清楚

改排期**不在**上面那三个动作里 —— 看板交给第三方扩展的能力面（`host.tasks`）上只有
`create` / `patchContent` / `setStatus`，排期没开口子。它只存在于看板自己的**同源 action 通道**上：

```
浏览器 ──POST /api/task-board/action──► 任务看板
          { requestId, action: { kind: 'set-schedule', taskId, patch } }
```

**这是正当的，不是绕闸。** 那条通道本来就有两个平等的调用方，看板源码里
`applyBoardAction` 的注释原话是 *Provider capability calls and the same-origin wire both
land here, so the two surfaces can never disagree about a card* —— 两条路进的是同一个校验函数。
而且它有自己的闸：`browserSameOriginMarker` 要求请求带着浏览器的同源标记，非回环地址还会
再查 Host 和代理令牌。我们在浏览器里发，这些头部是浏览器自己加的，不是伪造的。

**代价，摆在明处：** 这是比扩展契约**更低一层**的接口。字段名对不上、或者看板哪天改了路径，
这一块就会失灵。所以只发 `set-schedule` 这一个动作；失败时把看板自己的原话带回来；
路由不在时控件全灰、原因写在控件上。

另外这一条跟前面三条**不是同一个就绪信号**：前面那条问的是「看板的扩展面通不通」，
这一条直接去探看板自己的路由（账本被另一个 DSH 进程占着时，服务在、路由不在）。

**新建时也能排期，但那是两次调用。** 看板的新建接口不收排期，所以「新建任务」里勾上
排期之后，流程是「先建卡拿到 id → 再拿这个 id 去排」。中间那一步可能失败，界面**不藏它**：
卡是真建出来了，那就照实说卡建好了、排期没排上、为什么（提示条也用「没全成」的颜色），
并且照样把卡打开。假装整个失败是最糟的 —— 用户会再建一张，留下一张谁也不认识的孤儿卡。

## 会话

抽屉的「会话」那一页里嵌的是**宿主真正的会话页本体**——消息气泡、工具卡片、
正在跑的指示、底部输入框，全都是宿主自己那份，可以在里面接着对话。

这件事一度以为做不到，理由是「`conversation.content` 是单工厂座位，第三方注册不了」。
**注册不了是真，但根本不用注册。** 它是一个 **Component Factory**：宿主定义一次，
谁都可以渲染一份 occurrence。钥匙是 `renderFactorySlot`，不在 ctx 上、也不用 import，
是渲染器**白送给每个座位组件的 kit prop**。宿主的 `ui-subagent` 就是这么把同一份
会话页渲进右侧栏的，官方 README 原话是 renders the shared Factory。

唯一的门槛写在官方 README 的 Known Limitations 里：**factory 不接受独立的 sessionId，
会话身份只能从渲染位置继承**。所以要在外面套一层 `SessionProvider`（它也是 kit prop，
但**有条件**：注册座位时声明了非 root 的 session 子座位才发——所以本插件注册 `main`
时多声明了一个 session 子座位，纯粹为了换到这个东西，一个组件都不往里注册）。

**外面包了一层自己的错误边界。** 宿主的渲染器对 `SlotAssemblyError` 是重新抛出的，
一路上去就是整片白屏；我们这层比它靠外，最坏情况退回下面的只读记录。

### 退路：一份自己画的只读记录

拿不到 kit props / 会话服务没有 `retain` / 会话读不到 / 渲染期抛错——这四种情况下
退回自己画的那份（`ctx.sessions.using` 读事件流，挑出人说的话），并且**说清是哪一种**。

样式上刻意朴素（没有头像、没有气泡尾巴），一眼看得出来它跟宿主那个不是同一个东西。

这份记录有第二个用途：归纳目标/场景时可以把它一起喂给模型（默认不带，勾了才带）。

### 抽屉头那个悬停气泡

「会话 id / 开始 / 现状」这三行原来是抽屉正文里的一块，现在挂在**标题的悬停气泡**上。
理由是位置：它们是关于这个任务的静态事实，不是内容，而抽屉存在的理由正是把聊天区放大。
气泡里还带着说明里那句描述。要打开宿主的会话页，用标题右边那个「打开会话」。

## 没有任务卡的会话，也当成任务

**大多数会话根本不挂卡** —— 随手问一句、临时排查一个报错、在一个窗口里连着聊半天。
它们一条都不出现在任务看板上，于是「我到底开了些什么」这件事，恰恰在最需要它的那个
插件里看不到。

所以本插件把宿主会话目录（`ctx.sessions.list`）读出来，投影成和账本卡**同一种形状**的行，
混进同一份索引。三个视图不用知道它们的来历，照常画：

| 页面 | 它们长什么样 |
|---|---|
| 看板 | 带一枚虚线「会话」角标。沉在本列最后 —— **「待审阅」列除外**，那一列问的正是「哪些窗口还没收工」，会话是它的正主 |
| 甘特 | 一行一根条，带「会话」小标，也排在最后；右上角有「隐藏会话」开关 |
| 进度 | 照常进「任务总数」和状态分布，另外单占一格「会话」 |

**归列**：在跑 → 「进行中」；**有东西在等它**（权限申请 / 提问 / 计划审批）→「待审阅」——
「在等」压过「在跑」，因为一个停在那儿等你的会话待在「进行中」里，恰恰会被人漏掉；
其余一律「待审阅」。

会话没有「已完成」这个概念，只有「在跑」和「停着」，而停着的那一堆里混着
「答完了」「聊到一半走开了」「等你回话」——**那一层由颜色回答，不由位置回答**。
位置只说一件事：这一格还没被你收走。收走的方式只有一种：归档，
而**归档只能由人来做，会话永远不会自己掉进去**。

**排除三类，一条都不能少：**

- **已经有卡的**：某张卡的执行记录里写着这个会话 id，那它已经以那张卡的身份出现过。
  不去重就是同一个东西数两遍。
- **空的**：宿主自己的 `blank` 判据 ——「这一格还没有任何内容」。刚点开、什么都没发的草稿
  不是任务。
- **子代理的**：`parentId` 有值、或者 `origin` 是 `subagent`。它们是某个会话内部派出去的分身，
  不是人开的窗口。

**它们基本是只读的**：没有账本，所以不能编辑、没有执行记录、没有排期。唯一能改的是**归档** ——
那句话没有别人能替我们说，所以它写在本插件自己的文件里（`$DSH_HOME/dsh-plugin-task-board/sessions.json`）。
拖到「归档」就是收工，拖回来就是撤销。**在跑的不许收工** —— 那等于把它的后半段藏起来。
界面上把该灰的都灰掉，而不是让人点了才发现不行。抽屉里也只剩「会话」一页 ——
另外三页的内容全都来自账本字段，会话一个都没有，留着就是三个空页。

## 卡片边框上的颜色

位置回答「它还在不在我的待办里」，颜色回答「它为什么停在这儿」。两者是正交的。

| 色 | 意思 | 信号 | 来源 |
|---|---|---|---|
| **红** | 这一轮没走完，你得看一眼 | `turn/end.reason.kind` ∈ `error` / `max-tokens` / `aborted` / `interrupted`；或者**开了头没下文**（见下） | 会话事件日志 |
| **橙** | 它**停住了**，等你做一个动作 | `pendingInteraction.kind` ∈ `approval` / `question` / `plan-review`；`goal.phase === 'blocked'` | 宿主实时推送 |
| **绿** | 它自己宣布目标达成 | 最后一条 `goal/change` 的 `goal.phase === 'complete'` | 会话事件日志 |
| **蓝** | 跑完一轮，轮到你了 | `reason.kind === 'completed'`（会话）／账本 `done` + 上次执行 `succeeded`（任务卡） | 会话事件日志 |
| **橙红呼吸** | **它下面还压着东西** | 它的子代理里有在等的 / 跑挂了的 | 会话目录的父子关系 |
| **闲着**（中性） | 没什么动静 | 上面几条一条都没沾上，**而且确实没有消息**：没跑完过一整轮，或者读不出来 | 兜底 |

最后那一行是**兜底，不是信号**，它有两条边界：只管「待审阅」那一列（同样一张卡在「进行中」
就是还在跑、在「待办」就是还没开跑，那时候「闲着」根本不是一种状态）；读不出来的时候
照给颜色，但气泡里明说「上一轮的结论没读出来」—— 不写成「它没跑过一整轮」，那是我们
编的，不是我们读到的。

**跑完了不许叫「闲着」。** 蓝色只管「跑完了」，**看没看过不另算一种颜色** ——
`completionUnread` 只决定气泡里说不说「你还没看」。以前看过的那一半落进闲着色，
于是「完成了任务」的窗口顶着「没什么特别的事，就等你收工」（用户 2026-10-14 说
「有些会话窗口是完成任务了的，但是在你的定义里是闲着」）。同样的口径也管任务卡：
账本 `done` + 上次执行 `succeeded` 跟会话跑完一轮是同一种意思，**两边一种颜色**。

**两种动法。** 纯色那几种（红 / 橙 / 绿 / 蓝 / 闲着）是**跑马灯**：底色仍然是那个色，
一小段亮光贴着边框跑，1.5 秒一圈。橙红那条（子代理压着）是另一种：它整条边在红和橙
之间来回（1.6 秒一个来回），因为它的意思是「藏起来的东西在叫你」，跟「这一轮怎么了」
不是一回事。

**光是「跑」还是「闪」，全看带宽和速度。** 光带原本占掉整圈的三分之一（240° 之后一路
淡下去），一圈 3 秒；落在边框上任意一点看，就是「慢慢变亮、再慢慢变暗」—— 那是呼吸，
不是跑马灯。用户 2026-10-14 先报「呼吸太慢了不仔细看都看不出来闪烁效果」，紧跟着一句
「我记得我已经让你改成跑马灯的效果，怎么又变成呼吸的效果了」：东西确实是跑马灯
（角度一直在走），但**眼睛不这么看**。收窄到 70° 往回淡、一圈 1.5 秒之后才读得出是跑的。
一条上限断言钉着（超过 2 秒就红），另一条钉着淡出的弧度不许超过 80°。

实现上有两处值得记：光的角度得靠 `@property` 把它注册成 `<angle>` 才插得了值（不注册就
只能硬切，画出来是不动的）；边框那一圈是**画成背景**的，不是 `::after` —— `.card` 上有
`overflow:hidden`（裁工作区那条斜带用的），`::after` 只要伸到边框那一圈就会被整个裁掉。
所以真边框设成透明，内芯裁 padding-box、那一圈裁 border-box，露出来的正好是边框本身。

那道光**两个主题都往白走**。浅色主题早先反着往深走，理由是「卡片底色本来就是白的，
往白走等于融进白底」—— 那个理由看错了对象：会融进白底的是卡片底色，而这道光画在
**边框那一圈**上，那一圈本身就是饱和的颜色，往白走在浅色下照样看得见；往深走反而只是
「这条边在那儿略深一点点」。用户 2026-10-14 报的就是这个（原话「如果是浅色外观或者
跟随系统属于白天的时候，跑马灯的效果不太明显」）。实测两个相位之间的最大通道差：
往深走 89，往白走 158（深色同口径 146）。两边都留着色相，所以红的还是红、蓝的还是蓝。
两边都留着色相，所以红的还是红、蓝还是蓝。
CSS 里是一条 `:not(.tone-cascade)` 规则覆盖全部纯色，以后再加颜色自动就有呼吸。

系统辅助功能里开着「减弱动态」时，所有动画都关掉、颜色留着 —— 关成没颜色等于把
这一类藏起来了。

**判断只看机器码。** 宿主的 `LlmError` 带一个稳定码（`SERVER` / `TRANSPORT` / `TIMEOUT` /
`RATE_LIMIT` / `QUOTA` / `ACCOUNT_QUOTA` / `AUTH` / `INVALID_CREDENTIAL` / `NO_ADAPTER` /
`CONTEXT_WINDOW_EXCEEDED` …），源码注释原话是 *"route on this, never by parsing `message`"*。
所以代码里**一个字符都不解析错误文本** —— 原文只用来显示，从来不用来判断。

**「开了头没下文」也是红的那一种。** 日志里有 `turn/start`、往新翻再没有配对的 `turn/end` ——
一轮还开着，进程就被硬杀了（强退、断电、崩）。软退出不算：宿主关应用时会补一条
`aborted/disposed`，那走上面那条路。

这一条有个坑：**它跟「它此刻正在跑」在日志里一模一样**（都是「有开头、没结尾」）。
所以宿主半体只报「候选」（`unfinishedAt`），**是不是事故由浏览器半体凭会话目录里的
`running` 定夺** —— 判错了会很难看：一个正在跑的会话顶着红框，或者一个被硬杀的会话
一片安静。翻案过的那个会话这一格就是「没有结论」，不回退到更早那条 `turn/end`
（它说的是上一轮，而上一轮已经被这一轮顶掉了）。

顺带：这类会话**往回翻的页数放宽到 8 页**（原来 3 页 / 600 条）。被硬杀的往往是长轮次，
`turn/start` 离尾巴一两千条，翻 3 页够不着 —— 于是「被杀」看起来跟「没跑过」一模一样。
代价只落在**没有 `turn/end` 的会话**上：有结论的会话第一页就返回了，一条都不多读。

**读不出来 ≠ 出了事。** 两者在下游长得一样（都没颜色），但意思完全不同：
一个是「它还没跑完过一整轮」，一个是「我读不出来，你别信我」。所以这两种分开报，
页面顶上有一条横幅专门说后一种。

**绿色读的是事件，不是投影。** 宿主有一个 `goal` 投影，上面也有 `phase`，本来走它更顺。
不走的原因有两条：那个投影**按需懒加载**，给板上二十个会话各要一次是要发请求的；
而宿主半体为了拿 `turn/end` 本来就要读会话事件日志，目标的最后一条变化就躺在同一份日志里
（`goal/change`）—— **不新增任何一次读盘**。

两个坑：目标的最后一条变化经常排在最后一次 `turn/end` **之前**（先宣布达成，那一轮才结束），
扫到 `turn/end` 就停下会把它整个漏掉；`operation: 'clear'` 那条里**没有 `goal`**，
只能看到 `cleared`，这时要报「没有目标」而不是把上一轮那个 `active` 留着。

**为什么这件事要单独做一条宿主路由。** `turn/end.reason` **不在任何一个投影里**
（投影只有 `turnOutline` / `turnBoundary` / `subagentCatalog`），浏览器半体根本拿不到。
任务看板的宿主半体读到同一个字段，但读完就压成一句 `"agent turn ended with an error"`
写进账本 —— 真实账本里那条就是这个字符串，`QUOTA` 和 `SERVER` 全被抹平了。
所以本插件的宿主半体自己去读会话事件（走宿主的 `typertGateway`，跟看板同一层、
同一个方法），把每个会话最近一次的结论端给前端，按 `(会话, 最新序号)` 缓存。

**三条路各自供自己那份颜色，掐掉哪一条都不影响另外两条：**

| 掐掉 | 少了 | 还在 |
|---|---|---|
| `uiSession` 不在场 | 橙、橙红呼吸、气泡里的「你还没看」 | 红、蓝（都只读会话事件，不受影响） |
| 事实路由不在 / 读失败 | 红、蓝 | 橙、橙红呼吸（当下那条路不受影响）—— 待审阅里那些兜底的卡颜色照旧，只是气泡改说「读不到」 |
| 账本不在 | 卡自己的颜色 | 会话的颜色一律照常 |

任何一种情况下**列、排序、筛选全都照常**，并且页面上有一条横幅说明少了什么。绝不因为
读不到就把页面弄空 —— 这一条是插件的地基。

## 收工（归档）

**这是唯一一处本插件会写会话状态的地方。**

- **卡**：走看板账本的 `archivedAt`。归档会解除排期、看板自己的 archive view 也看得到、
  能恢复。写入走的是看板自己的同源 action 通道（`{kind:'archive'|'restore'}`）——
  因为扩展面的 `host.tasks` 上**没有**归档这个动作。
- **会话**：账本里没有会话这种东西，所以写在本插件自己的
  `$DSH_HOME/dsh-plugin-task-board/sessions.json` 里。

**归档只能由人做。** 会话永远不会自己掉进「归档」列。在跑的不许收工 —— 那等于把它的
后半段藏起来，而它跑完的那一刻恰恰是最需要你看的。

**「待审阅」是一条从旧到新的队列，不分节。** 按「它是什么时候停下来的」正序排，
最早停的在最上面 —— 这一列问的是「哪个窗口我还没收工」，而最容易被忘掉的恰恰是
最早停下来那个，倒序等于把最该看的压到最底下。这个时刻就是卡片第四行写出来的那个
（会话写「活动」、任务卡写「结算」），三者一致，卡上写的和排的顺序不是两回事。

**只有「归档」按天分组。** 分组和「最早的在最上面」本来是打架的：按天分完，组内再
怎么排，跨过组边界那条顺序就断了。归档那一列是只增不减的历史，按天折 + 默认只展开
最近 7 个工作日才收得住，更早的点「更多」。

**卡上不摆会话 id。** 那串十六进制对人没有任何用，想认哪个会话看标题就够了。
要看 id 去悬停气泡或者抽屉里 —— 那两处的是给人复制用的，不是摆在脸上当装饰的。

## 已知缺口

### 原型里那些字段，账本里没有

**不是没写，是真实数据模型里没有对应字段。** 硬做只能自己编一套数出来显示，那比不做更糟。
现在绝大多数都补出来了（办法见上面「目标 / 场景 / 背景 / 验收 是怎么来的」），补不出来、
或者补出来会误导人的才留在这里：

| 原型里有 | 现在怎么办 |
|---|---|
| 卡片上的「优先级」徽章 | 有了，规则算的（不用模型） |
| 卡片上的「周目标 / 月目标」徽章 | 换成了排期频率：「每天 / 每周 / 每月」，由 cron 反推。**单次规则没有周期**，不挂这枚标 |
| 卡片上的「手动结算」徽章 | 有了，判据是**列状态与最近一次执行结果矛盾**，是真的推得出来的 |
| 卡片上的「缺目标」小黄点 | 有了，执行提示和说明都空着时才亮 |
| 抽屉的目标 / 场景 / 背景 / 验收 | 有了，三级来源（规则 → 模型 → 人改） |
| 进度视图的「周期目标」卡 | 换成了「本期跑动」，但**目标是真算出来的**（见上），不是编的 |
| 工作区卡的「本周目标 x/y」 | 同上 |
| 抽屉的「编排进度」块、卡片上的编排徽章 | 没有编排概念 |
| 「任务看板」动作/编排那几套模态框 | 同上 |

### 做不了的（技术上挡住）

- **抽屉里没有「子代理会话」页。** 原型里它是第五个标签。那棵树归
  `@deepseek-ai/dsh-client-ui-subagent` 所有，数据来自它自己的 `subagent/catalog` 投影，
  只有直接子级、第三方塞不进去。（顺带一提：那个包**内部**的侧边栏聊天用的正是
  本插件嵌会话页的同一个办法，所以「嵌宿主的东西」本身不再是障碍，
  挡住的只是它的**数据**。）

### 明确放下的

- **编排视图。** 原型里有过一版，用户说先不考虑了。
- **拖拽挪列只做了看板那一层。** 甘特图上直接拖着条形改期没有——账本里排期是 cron，
  「拖一下」对应的语义不唯一（是推迟这一次，还是改规则？），想清楚之前不做。

## 开发

```bash
npm install
npm run build     # → lib/index.js（宿主半体）+ lib/client.js（浏览器半体）
npm run verify    # 提交前自检，见下
```

`lib/` 是**提交进仓库**的，用户装下来就地生效、没有构建步骤。代价是改完 `src/`
必须重新 `build` 再提交，所以 `npm run verify` 会检查 `lib/` 比 `src/` 新。

`npm run verify` 查三件事，每件都对应一次真出过的事：

1. 浏览器半体的 `window.__ModuleLoader__.load({ id, factory })` 里 **id 等于包名**，
   且 `load` 只调一次。写错 id 的后果是页面一片空白、控制台一声不响。
2. `lib/` 比 `src/` 新（防止把旧产物发出去）。
3. 拿假 webServer / 假模型 / 假看板调一遍宿主半体的 `apply`：路由都注册上了、真实账本
   读得出来、模型乱回话时退回空、脏的请求体被挡在盘外、看板不在场时写入口是关的且
   **说得清原因**。

第 3 步会真的往磁盘写文件（归纳缓存、人工改动），所以那一段开始前把 `DSH_HOME`
换成一个临时目录——自检不该在你的 `~/.dsh` 里留东西。

界面那一半另外有一套浏览器套件（headless Chrome 真渲染 + 真点击，564 条断言），
在 `/tmp/dsptb-client/`，不进仓库。

`npm run build` 打包前会先跑一遍 `tsc`。esbuild 只转译不做类型检查，有些错它能
照单全收地打出语法完全合法的 bundle（最典型的是 CSS 模板字符串里混进反引号），
所以类型没过就直接停，不往下走。

### 代码怎么分层

```
src/index.ts               宿主半体：读账本快照兜底 + 归纳路由 + 人工改动的存读 + 会话事实 / 会话归档两条路由
src/enrich.ts              宿主这半边的模型调用：提示词、防御性解析、超时
src/sessionfacts.ts        宿主半体读会话事件日志：每个会话最近一轮是怎么结束的
                           （那个字段不在任何投影里，只能从这儿读 —— 见上面那张表）
src/client/index.tsx       浏览器半体入口：注册侧边栏那一行 + 主区域页面
src/client/data.ts         数据源解析（看板服务 → 账本 → 明说拿不到）
src/client/model.ts        三个视图共用的纯函数推导
src/client/derive.ts       「账本里没有、但推得出来」的那些字段（目标/场景/背景/验收/优先级/周期目标）
src/client/enrich.ts       模型那条路的客户端：素材攒装、缓存、人工改动的取送
src/client/session.ts      只读会话记录：ctx.sessions.using + 从事件流里挑人话
src/client/sessions.ts     会话目录 → 任务行：没有卡的会话也进三个视图，四类排除规则在这儿
src/client/signals.ts      三路会话信号的汇总：宿主实时推的、宿主半体读的、你归档过的
src/client/tone.ts         「它为什么停在这儿」：卡片边框颜色的纯函数，判断只看机器码
src/client/write.ts        写那条路的客户端：就绪探测、动作发送、看板拒绝的原话
                           （归档卡走看板的同源 action，跟排期一样）
src/client/styles.ts       全部样式，颜色只读宿主的 --dsw-* 令牌
src/client/views/*.tsx     三个视图 + 抽屉 + 新建/编辑表单
```

**推导层（`derive.ts`）为什么单独一个文件。** 它是这个插件里唯一「说账本没说的话」
的地方，所以规矩要写在一处、检查在一处：不许出现账本里没有的事实；推不出来就标
`missing`，让界面显式说「没有」，而不是显示空白。三个视图各写一遍的话，
迟早会有一处开始编。

**颜色一个都不自己调。** 全部读宿主 ui-theme 的 `--dsw-alias-*` 变量，
所以深浅两套色自动跟着宿主走，用户切主题时不需要重新挂载任何东西。
